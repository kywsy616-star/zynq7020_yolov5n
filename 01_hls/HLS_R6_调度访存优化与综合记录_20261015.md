## R6.1：保留R5实现，增加阶段测量标记

### 1. 前提、范围与版本命名

1. 基线是已经上板验证的 **R5 / 7.xsa**：100 MHz、`xc7z020-clg400-2`、整网约237 ms、
   稳态约4.212 FPS。现有逐算子profile中整网为237185 us，84条单次调用之和237194 us。
   CPU侧仍是AMP v3：CPU0 pre/PL、CPU1 post/display。
2. **R6.1只做测量标记，不做加速改造。**
   保留CO=16、CI=4、NX=16、一套MAC、原tile策略、循环次序、缓存、数据类型、
   量化运算和AXI搬运配置。
   模型、84条描述符、权重724544 B、requant 36096 B、arena 5745408 B均不改；
   不增加DATAFLOW、双缓冲或64位gmem。
3. 本轮修改HLS源码和测试/综合脚本，新增一个只输出的阶段事件接口。
   **不修改Vivado工程、Vitis软件、摄像头/HDMI及AMP调度；
   不代为导出IP、生成bitstream或XSA。**
   C仿真与独立HLS综合用于验证标记可综合和数值一致性。
4. 后续由用户将本轮RTL导出为HLS IP，再在Vivado更新并导出硬件平台。
   该版本XSA按要求记为 **`7_1.xsa`**；
   沿用当前工程完整文件名时为 **`yolov5n_speed_wrapper_7_1.xsa`**。
   XSA是Vivado的硬件交接文件，不是HLS直接生成的IP包。
   本轮尚未生成，也尚无7_1.xsa板测结果。
5. **有阶段标记不等于已经有阶段耗时。**
   本轮没有内部自由运行周期计数器、阶段累计寄存器或串口打印。
   后续必须接同一`ap_clk`下的外部计数器/ILA，才能测阶段周期。
   保持现有Vitis时，只继续显示原有整网/逐算子计时。
6. 插入标记会让HLS重新调度，可能增加少量状态和周期。
   因此R6.1测到的是“带观测标记的R5实现”，不能预先宣称周期与原7.xsa完全相同。
   部署后先比较相同条件下的整网、op0/3/6/67，再解释阶段占比；本轮不承诺FPS提升。

修改前的R5源文件、头文件、测试与摘要已冻结在 [pre_R6_1_20261015][r6-link-02]，

### 2. 为什么先测这些阶段

R5全网补齐通道后的MAC为670728192，按100 MHz、每周期64 MAC计算，纯MAC理想账为104.801 ms；
实测237.185 ms。差额包含加载、参数选择、计算循环控制/流水线启停、重量化、残差、
写回和总线等待，不能全部归为DDR耗时。

| 优先观察算子 | R5实测 | 补齐通道后的纯MAC理想账 | 目的 |
|---|---:|---:|---|
| op0，stem 3×3 | 18.816 ms | 4.424 ms | 定位大分辨率输入搬运与小通道计算的额外开销 |
| op3，1×1 | 4.705 ms | 0.492 ms | 观察短计算块的初始化、重量化和短写回占比 |
| op6，1×1 | 10.290 ms | 1.966 ms | 观察较大输入/输出通道下的阶段占比 |
| op67，Detect 3×3 | 22.231 ms | 17.695 ms | 对照较高MAC占比算子，识别可优化上限 |

op0的RGB有效MAC为`192×256×16×3×3×3=21.234M`，除以6.4 GMAC/s得到3.318 ms；
实际HLS仍执行补齐后的IC=4，计数应为28.312M / 6.4 = 4.424 ms。
上述理想账均不含流水线启停、外围循环及其他阶段；
不能把3.318 ms直接当作当前硬件的整算子目标。

### 3. 新增接口与事件定义

顶层函数仍名为`yolov5n_top`，追加`volatile uint16_t *profile_event`，
接口模式为 **`ap_ovld`**。
RTL的有效输出为16位`profile_event_o`和1位 `profile_event_o_ap_vld`；
没有ready/ack或输入valid，监测端不形成反压，也不把日志写入DDR。
HLS还推断一个不参与计算的16位`profile_event_i`输入，后续在Vivado用16位常量0连接。

```text
profile_event_o[15:8] = op编号（0..83）；0xff表示调用级事件
profile_event_o[ 7:0] = phase编号
仅在 profile_event_o_ap_vld == 1 的时钟沿采样事件数据
```

**不能把事件数据当成持续有效的phase电平。**
外部接收逻辑要在valid时锁存事件，并在无新事件的周期保持上一次phase/op。
连续两拍valid也必须逐拍接收，不能只检测valid上升沿。

| phase | 头文件名称 | 事件位置与阶段含义 |
|---:|---|---|
| 0 | CALL_BEGIN | 顶层调用开始，op=0xff |
| 1 | DESCRIPTOR | 当前op描述符读取开始 |
| 2 | DISPATCH | 描述符解析后，进入合法性检查/分发 |
| 3 | WEIGHTS | Conv整算子权重加载开始 |
| 4 | RQ_LOAD | 整算子requant参数加载开始 |
| 5 | INPUT_TILE | 每个输入tile搬运开始，含halo补零 |
| 6 | BLOCK_INIT | 每个(x0,ob)块的片上参数选择、bias初始化开始 |
| 7 | MAC | 每个块的ib/ky/kx/nx计算区域开始 |
| 8 | RESIDUAL | 有残差时的块级残差预取开始；无残差不发此事件 |
| 9 | REQUANT | 块级重量化、激活、残差相加和打包开始 |
| 10 | OUTPUT | 块级DDR写回开始 |
| 11 | CONV_CONTROL | 块写回循环后，进入后续块/tile的循环控制 |
| 12 | POOL | MaxPool调用开始；本轮不拆其内部阶段 |
| 13 | COPY | Copy/Upsample调用开始；本轮不拆其内部阶段 |
| 14 | OP_END | 当前算子函数返回或非法描述符跳过后 |
| 15 | CALL_END | 顶层调用结束，op=0xff；n_ops=0也输出 |
| 16 | INVALID | 原有检查判定非法描述符，随后跳过；校验规则未改变 |

Conv通常序列为：

```text
DESCRIPTOR → DISPATCH → WEIGHTS → RQ_LOAD → INPUT_TILE
→ BLOCK_INIT → MAC → [RESIDUAL] → REQUANT → OUTPUT → CONV_CONTROL
```

然后重复块/tile阶段，最后`OP_END→...→CALL_END`。
这些事件覆盖所有算子，不只覆盖4个优先观察的算子。

事件通过`volatile`保留中间写入；普通非volatile输出可能仅保留最后一次写入。
依据：[AMD UG1399 2020.2：Multi-Access Pointers on the Interface][r6-link-03]。
C仿真只能看到最终事件，不能验证事件在真实时钟上的间隔；需结合生成RTL及后续RTL/板级观测。

本机2020.2实测发现：本工程的原生volatile指针跨非内联函数传递时，会插入无用读操作。
若用`ap_vld`会产生`*_i_ap_vld`输入等待；
该候选归档在 `archive/r6_1_marker_probe/rejected_native_volatile`。
`volatile ap_uint<16>`候选虽无输入口，但中间事件会被优化掉，仅剩CALL_END，也已弃用归档。
最终使用原生`volatile uint16_t`保留每次写入，
并用`ap_ovld`让推断的输入半口采用无握手的 ap_none语义，消除输入valid等待；
输入数据不参与任何计算。
部署时将`profile_event_i`接常量0，采集`profile_event_o`及`profile_event_o_ap_vld`。

### 4. Vivado后续如何接入及原因（本轮未修改）

用户后续更新IP后，保留原AXI-Lite地址、gmem连接、HP端口、100 MHz时钟及复位关系。
新增输出必须接入可观测逻辑，否则Vivado可能裁掉未使用的标记信号。

建议分两步：

1. 用与HLS同源的`ap_clk`驱动一个自由运行的64位周期计数器，
   接入`profile_event_o`和`profile_event_o_ap_vld`，
   将`profile_event_i[15:0]`接`xlconstant`的16位零值。复位与HLS一致；
   跨时钟采样需另做CDC，不能直接跨域锁存事件总线。
2. 先选一个目标op，按phase累计相邻事件之间的真实时钟数，在OP_END时冻结结果；
   ILA/VIO读取结果可不改现有Vitis。
   如希望由PS读出并串口打印，后续还需计数器的AXI-Lite读回接口及Vitis读取代码，
   这不属于本轮。

计数规则：对事件`E_i`在时钟`T_i`锁存，`T_(i+1)-T_i`归入`E_i`的phase；重复phase间隔累加。
所有阶段的区间和应等于DESCRIPTOR到OP_END的时间，CALL_BEGIN/CALL_END用于校验调用包络。
CALL_END之后关闭累计，下一次调用重新开始。
统一使用半开区间`[T_i,T_(i+1))`避免每次切换重复计数一拍。

换算式：`time_ms = cycles / (f_clk_MHz × 1000)`；100 MHz时`100000 cycles = 1 ms`。
时钟频率取Vivado实际接入值，HLS的10 ns综合约束不能代替实际频率。

如直接用ILA，应同时观察事件、valid和**自由运行计数器时间戳**。
启用valid限定采样后，压缩波形中的相邻采样点不再相隔一个真实周期，必须用时间戳相减。
op0约1.88M周期，普通小深度ILA逐周期捕获不足以覆盖整层；
优先硬件累计或按事件压缩，不能把采样深度不足解释为阶段已经结束。

**测量解释边界：** 阶段时间是事件之间的实际RTL调度区间，包含流水线填充/排空、
控制和遇到的总线等待。标记只约束事件先后，不强制所有非volatile运算留在源码所写的阶段内；
HLS可能将参数读取/地址计算提前，或将尾部运算延后。
因而BLOCK_INIT区间短，不等于所有初始化只花这么多周期；归因还需结合调度报告。
MAC段也包含ib/ky/kx控制，INPUT_TILE包含补零；OUTPUT段不是纯DDR写响应延迟。
HLS的AXI outstanding允许事务跨阶段，标记不是内存完成屏障；
若要精确区分AR/R或AW/W/B停顿，需要另监测AXI握手，不能仅凭阶段时间断言DDR带宽利用率。

先在与R5相同的逐op模式下测op0/3/6/67，再测正常AMP流水。
现有PROFILE_OPS在CPU1唤醒前执行，但摄像头/显示DMA已经运行；
启动arena为零输入，非相机预处理后的真实帧。
两种模式的DDR竞争不同，结果需分列，不能混成一个基线。

#### 5.3 RTL协同仿真与事件波形

采用两个小用例做XSIM C/RTL协同仿真：4×4的1×1卷积、3×5的3×3残差卷积。

完整模型数值回归使用C仿真；小规模RTL仿真不等于整网RTL仿真或板测。

requant/table各16384个int32。

### 7. R6.1板级ILA重新抓取、分析与计算（20:02:17）

#### 7.1 ILA设计过程与此次设置

HLS在关键阶段用`profile_mark`输出16位“op编号+phase编号”，同时输出valid；
Vivado中将不用的`profile_event_i`接16位常量0，`profile_event_o[15:0]`接ILA的probe0、
valid接probe1，自由运行的64位Binary Counter输出接probe2；
HLS、计数器、ILA均接PS的同一条`FCLK_CLK0`，实际为100 MHz。
由于整层持续约188万周期，1024深度ILA无法逐周期覆盖，
故采用**valid为1时才存储事件**的压缩采样方式，并同时保存计数器时间戳；
以`event=0x0001 AND valid=1`触发op0描述符开始，触发位置设为0，向后采集1024条有效事件。
分析时用相邻时间戳之差恢复真实阶段周期，而不是用压缩波形上两个点的横向距离当真实时间。
计数器可以自由运行，无需每层清零，同源时钟下相减即可。

本次采集：`CONTROL.CAPTURE_MODE=BASIC`，capture条件为`valid==1`；
trigger为`event==16'h0001`且`valid==1`，均按AND；
`CONTROL.TRIGGER_POSITION=0`，`CONTROL.DATA_DEPTH=1024`。
目录中的`ila_properties_before.txt`记录的是**修改设置之前**的ALWAYS/trigger position
512状态，不是最终抓取配置。1024个样本中valid始终为1属于压缩采样的正常结果。

#### 7.4 op0理想MAC账与完整算子的外推

从当前真实描述符读取：输入384×512、IC=4（RGB补齐），输出192×256、OC=16，K=3、S=2、
pad=1，tile=16×16；`CO=16, CI=4, NX=16`。

```text
RGB有效MAC = 192×256×16×3×3×3 = 21233664
有效RGB理想时间 = 21233664 / (64×100000000) = 3.31776 ms
实际补齐MAC = 192×256×16×4×3×3 = 28311552
当前硬件纯MAC理想时间 = 28311552 / (64×100000000) = 4.42368 ms

tile数 = ceil(192/16) × ceil(256/16) = 192
计算块数 = 192 × (256/16) × (16/16) = 3072
每块纯MAC发起周期 = (IC/4) × K² × NX = 1×9×16 = 144
每块MAC标记区间 = 172 cycles
MAC区间额外周期 = 172−144 = 28 cycles/block
全层该差额 = 28×3072/100000 = 0.86016 ms
```

28周期差额包含计算区域外围控制和流水线启停等，不宜全部归到某一个原因。

#### 7.5 输出为什么比MAC慢，以及下一步应测什么

R6.1每个块输出`16 pixels × 16 channels = 256 B`，C4布局下分成4段，每段16个32位字=64 B；
不同C4平面相距`oh×ow`个word，不能直接拼成一个连续burst。
全op0共有`3072×4=12288`个这样的源码连续写回段。
它们通常对应短burst，但**本次未监测AWLEN，12288不是实测AXI事务计数**。

在32位100 MHz接口上，单块64个数据字连续发送至少需64周期，输出标记区间平均195.119周期；
差额131.119周期说明除了数据拍，还有明显接口/调度开销。
它不是已测得的“131周期DDR反压”，更不能证明物理DDR带宽已经饱和。
`max_write_burst_length=128`只是允许上限，不会把只访问16个连续字的循环自动变成128个字。

后续以`AWVALID&&AWREADY`统计写地址事务和`AWLEN+1`，以`WVALID&&WREADY`统计数据拍、
WLAST核对末拍；分别统计`AWVALID&&!AWREADY`、`WVALID&&!WREADY`及B响应等待。
读侧对应观察AR/R握手。相同方法抓op3、op6、op67，确定短计算1×1与高MAC卷积能否共同受益。
官方原理参考：[UG1399 2020.2 Burst优化][r6-link-21]。

看ILA时先把event设为十六进制，按高字节读op、低字节读phase；
例如`0007→0009`为op0的MAC区域。两点时间戳差172，即1.72 μs。
看到valid一直为1以及采样点等距属于限定采样后的显示方式，实际耗时仍由64位计数器相减确定。
检查完整层必须出现OP_END；
若深度耗尽仍停在块循环，应改为更稀疏的capture条件或硬件阶段累计，
不能把窗口长度当完整层时间。

#### 8.2 修改后：保留计算实现，在阶段入口写事件

```cpp
// R6.1：顶层追加参数，函数体设置接口pragma。
// 前面的p_act/p_wgt/p_rqt/p_tbl/start_op/n_ops保留。
// 新参数：volatile uint16_t *profile_event
#pragma HLS INTERFACE ap_ovld port=profile_event

static void profile_mark(volatile uint16_t *profile_event,
                         int op, hls_profile_phase phase)
{
#pragma HLS INLINE
    *profile_event = (uint16_t)(
        ((op & 0xff) << 8) | (int)phase);
}

// 以下为R6.1卷积阶段位置示意；省略各阶段循环。
profile_mark(profile_event, op, HLS_PHASE_MAC);
// 原MAC循环。
// 有残差时，还会发RESIDUAL事件并预取残差。
profile_mark(profile_event, op, HLS_PHASE_REQUANT);
// 原量化/激活/残差相加/打包循环。
profile_mark(profile_event, op, HLS_PHASE_OUTPUT);
// 原块级DDR写回循环。
```

这些标记用于测量，不改变乘加、量化及数据布局。
它们也不是计数器或AXI事务完成信号。
R6.1增加观测接口后需重新生成硬件；Vitis原控制用法保留。

#### 8.3 使用示例：C仿真、BD接法与ILA解码

没有新增需要软件写入的事件控制寄存器。

BD连接方式：`profile_event_i[15:0]`接16位常量0；
`profile_event_o[15:0]`、`profile_event_o_ap_vld`
和外部64位自由运行计数器接ILA。
IP、ILA及计数器使用相同的100 MHz时钟。

```text
仅在event_valid=1的时钟沿，取事件和计数器：
op    = (event >> 8) & 0xff
phase = event & 0xff

0x0007：op0进入MAC
0x0009：op0进入R6.1量化阶段
0x4307：op67进入MAC（0x43=67）
0xFF00 / 0xFF0F：一次HLS调用开始 / 结束

无残差的R6.1 MAC区间：
T = [counter(0x0009) - counter(0x0007)] / 100 MHz
例如差172周期，T=1.72 us。
```

事件信号建议用十六进制显示，计数器可用无符号十进制。
连续两拍valid都为1时，需要接收两次，不能只捕获valid上升沿。
有效事件过滤捕获时，横轴样本间距不代表真实周期；
时间必须用计数器差计算。
有残差时MAC的下一阶段是`08`，不能直接用`09`减`07`。
阶段完整定义见本版第3节，R6.2的编号变化见后文。

### 2. 代码组织与安全约束

**运行时选择原理（简述）：** HLS综合时，将代码中显式编写的容量计算、
比较和选择规则生成固定的硬件逻辑。
每条Conv开始时，IP从描述符获得通道数、图像尺寸、卷积核、步长及tile参数；
当`tile_c=16`且输出宽度大于16时，依次检查64宽、32宽候选所需的输入窗口能否装进现有BRAM，
候选宽度均受输出图像宽度限制。
选中的值存入内部变量`conv_tile_c`，用于控制后续tile横向步进和每行写回长度。
因此同一个IP可对不同层采用不同宽度，Vitis表中的`tile_c`仍保持原值；
运行时执行的是已综合的硬件规则，无需重新编译或重构FPGA。
缓存容量和16×4乘法阵列保持固定，MAC仍按NX=16分块计算，改变的是一次搬运、聚合的范围。

- 新增`HW_ROW_PIXELS=64`，采用`out_row[128/4][64]`共8192 B、双口BRAM；
  重量化直接写行缓存，没有再增加一次out_buf到BRAM的拷贝。
  原256 B完全分区输出寄存器缓存移除。
- 描述符`tile_c==16`时，优先尝试`min(ow,64)`，再尝试`min(ow,32)`，容量不足则保留16。
  检查公式为`(ic/4) × ((min(tile_r,oh)−1)×s+k) × ((候选宽度−1)×s+k) <= 13248 words`。
  不增加原ifm_buf深度；小于16等自定义tile宽保留，
  超过64的宽度按行缓存容量切成不超过64的内部tile。实际尾tile按剩余宽度处理。
- MAC循环、残差按块预取、数值运算次序保持；
  每个x0/ob块的量化结果写入 `out_row[oc_base/4+q][x0+nx]`。
  该tile的一行全部x0/ob完成后，再按`q→x`顺序一次写回，连续长度为`nc`，最大64个32位字。
- 同一行所有残差先按各自像素读取，行完成后才写输出，支持原地同通道残差；
  测试覆盖多ob、非16倍数真实通道、通道偏移、尾块与最大行缓存。
  没有将不同C4平面或不连续的图像行硬拼成一个burst。

op0的16×64输出tile需要输入`33×129×1=4257 words`，小于13248；
op1的64宽候选需要`33×129×4=17028`超限，32宽需要`33×65×4=8580`，故选32。
已有大通道层在容量不足时保留16，不能无条件把全网tile都改成64。

```text
R6.1: load tile16 → 每行 { 每x0/ob: MAC → requant → DDR写16像素 }
R6.2: load 容量允许的宽tile → 每行 {
           每x0/ob: MAC → requant并写行BRAM
           所有块完成 → 每C4平面连续写nc像素
       }
```

对于op0，tile数192→48，计算块数仍3072；
输出连续段长度16→64 words，源码写回段数12288→3072，输出总字节仍786432 B。
输入有效行的连续读段数也减少，但3×3/s2下64输出像素需129输入word，
超过现有max_read_burst_length=128，会发生拆分；
不能把源码段数直接当实际AXI事务数，也不能声称输入字节减少4倍。
正常边界下op0有效输入读取由208165 words降至203425 words，仅减少约2.28%，
主要期待减少短段控制开销。

### 3. 测量事件的版本区别

外部端口、valid和16位编码保持不变。
新增**phase17（0x11，HLS_PHASE_ROW_BUFFER）**表示“重量化、激活、残差相加、
打包并写入行BRAM”；R6.1的phase9仍保留定义，R6.2 Conv使用17。
**phase10仍表示实际DDR输出区域，但由每计算块一次改为每tile行一次。**
phase11出现在块控制和行写回后的控制处，不能再按R6.1每块固定次数估算。

R6.2序列为`5→{每行:[6→7→[8]→17→11]重复x0/ob，然后10→11}→...→14`。
op0的phase10次数预期为`48 tiles×16 rows=768`，phase17仍3072次。ILA接线不改；
事件解码/统计脚本需识别17，按实际事件时间戳重新计算，不能套用R6.1的201块外推公式。

### 9. 下一步优化方向与方案（本轮只记录，不改代码）

#### 9.1 优先做块间计算、量化和输出重叠

优先对象：op0/op3/op6以及同类1×1卷积。
op3的非MAC阶段占约75%，op0的量化和输出合计约5.216 ms；
目前它们与MAC按阶段串行，是比再次缓存小量权重更明确的优化空间。

建议先保留一套MAC和一套量化单元，引入两组累加结果缓冲及行输出缓冲：
计算块n+1时，让量化处理块n；计算下一行时，让访存单元写上一行。
缓冲采用生产/消费握手，消费者使用期间禁止生产者覆盖。
重点验证多ob、尾块、通道补齐、最后一行排空，以及同址残差先读后写的依赖。

当前多个指针共享`gmem`，2020.2不能直接在现有共享M_AXI结构上套DATAFLOW。
优先研究“单一访存任务管理gmem，计算/量化任务经片上通道交接”的结构，
避免多个DATAFLOW任务同时访问同一个M_AXI bundle，检查通道深度和死锁。
若能保持外部ABI，Vitis业务与BD接线可沿用；
若最终采用独立读/写AXI主口，Vivado需将两口接入相应SmartConnect/HP，
Vitis还需按新寄存器布局初始化新增指针，必须作为接口变更单独记录和验证。

验收先用相同输入比较R6.2与候选版全部arena，再做RTL AXI/事件对照和HLS综合，
确认MAC仍II=1、没有意外复制DSP；上板再比较整网和op0/3/6/67。
若总耗时下降而phase区间因并发重排，应使用各任务独立busy周期和完整包络验收，
不能继续把共享phase流简单相加当作并行阶段的独立耗时。

#### 9.3 根据AXI实测再决定64位接口和时钟

现有输入/输出已改善，下一步应按目标层采集AWLEN、AW/W/B与AR/R握手，
分别统计数据拍、短burst频次、VALID无READY的反压以及发起间隙。
先用局部触发窗口或AXI性能计数器，避免为了长时间抓全总线而占用大量ILA BRAM。

若确认持续传输位宽是主要限制，再将HLS gmem由32位改为64位，
保持C4内存布局并正确处理奇数word和边界；这会涉及HLS接口和Vivado互连更新。
指针/寄存器ABI保持时，Vitis算法可不变；数据对齐和缓存范围仍需核对。
DDR与VDMA竞争、短事务固定开销不会因位宽翻倍自动消失，不能承诺FPS翻倍。

当前HLS时钟域setup裕量只有0.178 ns，且整机HDMI域仍有违例，
不优先直接提高FCLK。HLS的目标周期只用于综合调度，不会自行改变板上时钟。
若后续确实提高PL时钟，需要同步Vivado时钟/复位/互连和XSA，并重新核对时序与ILA换算；
HDMI的动态时钟参考若仍与FCLK共用，还要检查对显示时钟生成的影响。

#### 9.4 优先级、收益目标与版本约定

   架构调度收益下降后，再评估MAC映射/并行度或模型计算量调整；模型修改需另做精度验证。

### 10. 修改前后代码示例与用法（2026-10-16补充）

#### 10.1 内部tile宽度：描述符16，硬件选择64/32/16

本节“修改前”指冻结的R6.1源码，
“修改后”指当前`src/yolov5n_top.cpp`。
示例省略无关阶段，不作为完整替换函数。

```cpp
// 修改前：Conv直接按Vitis描述符tile_c步进。
for (int tc = 0; tc < ow; tc += tile_c) {
    int nc = (tc + tile_c <= ow) ? tile_c : (ow - tc);
    // 搬运输入tile，计算nc列输出。
}
```

当前实现保留描述符，计算另一个内部宽度：

```cpp
int conv_tile_c = (tile_c < HW_ROW_PIXELS)
                ? tile_c : HW_ROW_PIXELS;
if (tile_c == NX && ow > tile_c) {
    const int max_nr = (tile_r < oh) ? tile_r : oh;
    const int row_words = icb * ((max_nr - 1) * ss + kk);
    const int wide_c = (ow < HW_ROW_PIXELS)
                     ? ow : HW_ROW_PIXELS;
    const int mid_c = (ow < HW_ROW_PIXELS / 2)
                    ? ow : HW_ROW_PIXELS / 2;
    if (row_words * ((wide_c - 1) * ss + kk)
        <= HW_IFM_WORDS)
        conv_tile_c = wide_c;
    else if (row_words * ((mid_c - 1) * ss + kk)
             <= HW_IFM_WORDS)
        conv_tile_c = mid_c;
}

for (int tc = 0; tc < ow; tc += conv_tile_c) {
    int nc = (tc + conv_tile_c <= ow)
           ? conv_tile_c : (ow - tc);
    // 后续输入搬运和行输出都使用实际宽度nc。
}
```

用法：Vitis描述符仍填`tile_c=16`，不用改为64。
上面的比较和选择是综合到PL中的硬件，逐算子执行，
不是板上运行HLS编译器，也不会回写DDR描述符。
只有默认16且输出更宽时才自动尝试扩大；
自定义小tile保留，超过64的自定义宽度受行缓存上限约束。
输入窗口仍必须符合本版第2节的容量前提。

`icb=ic/4`，`ss`是步长，`kk`是卷积核尺寸。
容量判定包含完整tile高度和halo，不只比较输出像素数。

| 本工程示例 | IFM容量判定，单位word | 内部宽度 |
|---|---|---:|
| op0 | 33×129×1=4257≤13248 | 64 |
| op1尝试64 | 33×129×4=17028>13248 | 不采用64 |
| op1再试32 | 33×65×4=8580≤13248 | 32 |

tile数是`ceil(oh/tile_r) × ceil(ow/conv_tile_c)`。
op0输出192×256、tile_r=16时，tile数从192降为48。
op1输出96×128、tile_r=16时，tile数从48降为24。
`NX=16`及64 MAC/周期不变；宽64的一行仍分4个x0块计算。

#### 10.2 输出聚合：块级寄存器写回改为整行BRAM写回

修改前，每个x0/ob块量化后立即执行DDR写回：

```cpp
uint32_t out_buf[NX][CO / CI];
#pragma HLS ARRAY_PARTITION variable=out_buf complete dim=0

// 以下位于每个(x0, ob)块内；省略计算及循环外壳。
out_buf[nx][q] = word;  // 量化并打包后的结果。
// 随后for q -> for nx执行块级写回：
dst_words[dst_base + nx] = out_buf[nx][q];
// dst_base包含oc_base和tc+x0，单段最多16 words。
```

修改后，量化结果直接写入8 KiB行缓存。
所有x0/ob块完成后，再按C4平面连续写出该tile行：

```cpp
uint32_t out_row[HW_MAX_OC / CI][HW_ROW_PIXELS];
#pragma HLS BIND_STORAGE variable=out_row type=ram_2p impl=bram

// 在(x0, ob)块内：量化并打包后写行缓存。
out_row[(oc_base >> 2) + q][x0 + nx] = word;

// 当前y行的所有x0/ob块完成后，才执行以下循环。
for (int q = 0; q < nwoc; q++) {
    const int dst_base = ((dst_ch_off >> 2) + q) * oh * ow
                       + (tr + y) * ow + tc;
    for (int x = 0; x < nc; x++) {
#pragma HLS PIPELINE II=1
        dst_words[dst_base + x] = out_row[q][x];
    }
}
```

第一维`oc_base/4+q`聚合不同输出通道块；
第二维`x0+nx`聚合同一行内不同空间块。
实际只写`nwoc=ceil(oc_real/4)`个C4平面和`nc`列，
不将整个32×64缓存无条件写回DDR。

内部宽64时，同一C4平面原来4组16 words的输出，
可以组织成64 words的连续区间，即256 B。
内部宽32时是32 words；尾tile使用实际`nc`。
数据量不变，量化/激活/残差运算顺序不变。
改变的是缓存位置、写回时机和连续区间长度。
不同C4平面仍分别写回；AXI还可能因4 KiB边界拆分。
该行缓存目前串行复用，不表示已经实现计算/输出重叠。

#### 10.3 新旧测量事件与板上使用方式

```text
R6.1块级：
07 MAC -> [08残差] -> 09量化 -> 0A块写回 -> 0B控制

R6.2块级：
07 MAC -> [08残差] -> 11量化并写行BRAM -> 0B控制
当前行的各x0/ob块重复上述步骤。
行就绪后：0A行写回 -> 0B控制。

以上均为低8位十六进制；11=十进制17。
例如op0的0011不是phase11，而是phase17。
```

无残差时，R6.2用`07→11`计算MAC阶段，
用`11→0B`计算量化及行缓存写入阶段，
用`0A→0B`计算行DDR输出阶段。
有残差时，MAC区间是`07→08`。
两个`0B`位置不同，分别对应块结束和行写回结束；
统计时需要结合前一个事件区分。

R6.2沿用R6.1的BD事件接线、valid采样和计数器用法。
Vitis仍使用原描述符、权重、量化参数及启动流程，
不新增控制字段。软件离线分析需识别phase17及行级phase10。
不能继续按R6.1的phase9或块写回次数解析本版。

本版部署结果归属`8.xsa`，现有文件名`7_2.xsa`保留；
下一次HLS实现大版本为`9.xsa`。
本次补充代码对照，并在当前HLS源码对应位置添加中文修改注释。
仅修改文档及注释，不改变接口、pragma、计算语句或调度逻辑，
不重新综合或导出IP；历史归档、板测及综合证据保持原样。

## R6.3：并行调度、输入预取与横向halo复用（9.xsa）

### 1. 本次范围与基线

基线为R6.2 / 8.xsa：整网198.426 ms，板测约5.04 FPS。
本版按用户要求实施三项通用优化：

1. 当前计算块MAC，与上一块量化及已完成行的输出重叠。
2. 计算当前tile时，分批预取下一tile的输入行。
3. 横向相邻tile保留重叠列，减少重复DDR读取。

1×1专用计算结构、模型通道或算子替换留到下一次。
通用调度覆盖现有Conv，1×1/3×3仍共用一个MAC任务。
保持100 MHz目标、一套16×4阵列、NX=16及原量化数值顺序。
不修改模型、描述符、权重、Vitis应用、摄像头或HDMI实现。

本次部署版本明确为 **9.xsa**。
XSA仍由用户在Vivado完成硬件流程后导出，
实现阶段只运行C仿真、纯HLS综合和RTL验证，不代为导出IP或XSA。
用户随后完成9.xsa部署，板测补充见第11节。
R6.2源码及记录已冻结到`archive/pre_R6_3_20261016/`。
R6.2综合复现脚本改读冻结源码，避免误综合当前R6.3。

### 2. 为什么使用分步并行调度

四个DDR指针仍共用`m_axi_gmem`。
原Conv不能直接拆成多个同时访问gmem的DATAFLOW任务。
本版将DDR访问集中给`r63_memory`，
`r63_mac`只读片上输入、权重及bias，
`r63_quant`只读片上累加器、残差及量化参数。
三个任务在`r63_wave`内并行，在每步结束后交接缓冲。

```text
步骤i：
memory：写已完成的旧行 + 读块i残差 + 预取下一tile部分行
MAC   ：计算块i，写当前acc bank
quant ：量化块i-1，读另一acc/res bank，写当前行缓存
        ↓ 三个任务均完成，才进入下一步
```

这不是无限制的跨块流水：每步仍有完成屏障。
DDR读取、残差和行写回在同一个访存任务内串行仲裁。
某一步访存过长，MAC仍会等待下一步；不宣称完全隐藏访存。
这样控制共享接口和缓冲生命周期，避免无界FIFO或反馈死锁。

### 3. 缓冲、所有权及残差安全

| 缓冲 | 用途 | 逻辑容量 |
|---|---|---:|
| 两套IFM | 当前tile计算、下一tile预取 | 2×52992 B |
| 两套acc | 当前块写入、上一块量化读取 | 2×1024 B |
| 两套res | 当前块残差预取、上一块量化读取 | 2×256 B |
| 两套out_row | 当前行组装、已完成行写回 | 2×8192 B |
| halo | 横向重叠列暂存 | 8192 B |

bank0在顶层声明并显式传入Conv/Pool/Copy。
这些算子逐个执行，因此仍可复用同一块scratch。
Conv只新增一个IFM bank；没有为Pool/Copy再保留第三份大缓存。
Pool/Copy仅调整内部缓存传参，原运算和tile循环保留。
顶层函数参数、AXI主口及AXI-Lite配置方式不变。

每步MAC写当前acc，量化读上一acc；残差也按相同bank交替。
残差在MAC计算当前块时预取，下一步量化才使用。
当上一行最后一个块已量化，之后的步骤才允许写回该行。
量化下一行与旧行写回使用不同out_row bank。
tile末尾额外两步排空末块量化和末行写回。

支持当前模型的源/目标分离，以及同地址、同通道位置的原地残差。
不扩展为任意移位重叠或Conv源输出任意别名支持。
下一tile的输入不能被当前tile的输出覆盖；真实模型已用完整arena回归。

### 4. 输入预取与横向复用的具体实现

内部宽度仍按R6.2容量检查选择64/32/16，Vitis继续传16。
根据当前tile计算块数量，将下一tile输入行分摊到各步：
每步额度为1、2、4、8或16行，用比较代替运行时整数除法。
这里“输入行”是一个C4通道组中的窗口行。
首tile必须先加载；末tile不预取不存在的后继tile。
自定义极短tile若未按预算预取完，会补齐后再切换bank。

相邻横向窗口重叠为`max(k-stride, 0)`列：
3×3/s1复用2列，3×3/s2复用1列，1×1/s1为0列。
保存旧tile最右重叠列，作为下一tile最左重叠列。
先读旧halo，再更新本行的新halo，避免覆盖未消费数据。
换到下一tile行时不复用旧halo；边界补零仍保持原语义。
如果重叠缓存超过2048 words，安全回退到DDR重读。
本版没有实现上下相邻tile的整行窗口复用。

即使低于10 ns，也不能据此宣称Vivado 100 MHz已经时序收敛。
9.xsa必须核对实现后的HLS时钟域及HDMI时钟域。

HLS估算不等于Vivado整机实际占用，原因沿用R5/R6.2说明。
尤其新增双缓冲会增加BRAM，整机还包含摄像头、HDMI和ILA。
必须以9.xsa对应的Vivado综合、布局布线资源及时序报告验收。
R6.2发现的HDMI时序问题本轮未修改，不能据HLS结果宣称已解决。

### 8. 几何预算、收益边界与下一步

按真实84条描述符核算，71条Conv的有效输入DDR预算为：

| 项目 | 32位word数 |
|---|---:|
| R6.2逐tile完整读取 | 1758317 |
| R6.3横向halo复用后 | 1749120 |
| 减少重复读取 | 9197 |

即减少36788 B，约0.523%的有效输入word。
这是源码几何预算，不是实际AXI burst数或板测带宽。
因此横向halo复用的整网收益应较小，不能独立声称省数毫秒。
主要收益期望来自阶段重叠及提前准备输入。

真实模型所有tile的预取额度均足够，无预算不足的补齐行；
首tile总计15181个C4输入行需要初始加载，
后继tile的24783行可安排在前一tile计算步骤内准备。
“可安排”不等于这些周期已完全隐藏，仍需看任务最长耗时及DDR竞争。

小用例实测周期减少3.25%～33.41%，收益取决于计算块长度和阶段比例。
不能把这个区间直接乘到整网198.426 ms，也不能据此宣称已达到某个FPS。
此前180 ms/5.56 FPS、170 ms/5.88 FPS仍仅是条件目标。
以上为实现阶段的预算；当时尚无整网RTL时延或9.xsa板测。
用户部署后的158.641 ms结果及ILA验证，已于2026-10-16补充到第11节。
后续串口应同时保留infer、fps/avg16及逐算子profile，
与8.xsa在相同FCLK和运行条件下比较。

下一次优先针对1×1卷积的短块控制/流水线开销，
依据本版RTL和后续9.xsa板测确定是否扩大调度粒度。
不把改变模型、减少MAC或复制更多DSP阵列混入本轮三项优化。

### 9. Vivado、Vitis及ILA用法

综合确认顶层接口和寄存器布局后，
Vivado只需更新HLS IP，保留现有gmem、AXI-Lite、时钟复位连接。
事件输入半口仍接16位常量0，ILA保持采样event、valid和外部计数器。
Vitis继续使用原指针、start_op/n_ops及tile_c=16；
需更新到9.xsa生成的平台和匹配bitstream，不需要新增参数初始化。

R6.3并行区新增事件：

| phase十进制 | 低8位十六进制 | 含义 |
|---:|:---:|---|
| 18 | 12 | 一步并行任务启动前 |
| 19 | 13 | 此步所有任务完成后 |

首tile加载仍由phase5开始，结束后发phase19。
描述符、权重、量化参数、OP_END和CALL_BEGIN/END保留。
并行区不再伪造单线程的MAC/量化/输出连续事件序列。
旧R6.1/R6.2解析脚本不能直接统计本版的阶段占比。

例如op67的`0x4312→0x4313`是一次并行步区间，
不是单独MAC、单独量化或单独DDR写回耗时。
ILA仍按每个valid有效沿采样，100 MHz用计数器差乘10 ns。
整算子优先测DESCRIPTOR到OP_END，整次调用测FF00到FF0F。
若要拆各任务活动，应在生成RTL中增加内部任务start/done/idle探针；
不能把重叠阶段耗时简单相加。

#### 11.3 ILA采样过程、事件与完整性

先保存用户当前4096点连续采样的原始`.ila`及CSV，再补抓有效事件。
BD确认IP、ILA及64位外部计数器同接PS FCLK_CLK0，时序报告为10 ns / 100 MHz。
Hardware Manager的`STATIC.ILA_CLOCK_FREQ=0`是未提供静态频率信息，不能解释成0 Hz。
采用BASIC模式、`valid=1`捕获、触发位置0，分别以op0/1/3/6/67的phase1触发。
每次保存4096个有效样点；最后用`event=XX0X AND valid=1`捕获1024个头事件，
过滤掉密集的phase18/19，让窗口覆盖两个以上整网并获取全部84个算子的边界。
这里只调整ILA运行时捕获条件，没有重综合、重新下载或改变硬件接线。
原配置保存在`hardware_properties.txt`，补抓过程见`capture_log.txt`和采样Tcl。
最后显示的是`network_headers.ila`，当前运行时捕获条件也为这个头事件过滤条件。

初始连续波形只有4095周期，即40.95 us；其中有效事件仅24个，属于op2。
两次valid之间看到的`0x0203`等旧值不能作为阶段持续时间。
解析必须先筛valid，再拆事件高8位op、低8位phase：

| 低8位 | 含义及本次用法 |
|:---:|---|
| 01、02 | 描述符阶段及分派边界 |
| 03、04 | 权重、量化参数加载阶段起点 |
| 05→13 | 首tile输入初始加载，13为十六进制phase19 |
| 12→13 | 一次并行步，十进制phase18→19 |
| 0E | OP_END；01→0E测完整算子 |
| FF00→FF0F | 完整调用边界，不能拆成普通op255 |

```text
耗时ms = (结束64位计数器 - 开始64位计数器) / 100000
输入tile数 = ceil(OH/tile_r) × ceil(OW/内部tile宽度)
每tile计算块数 = nr × ceil(nc/16) × (OC/16)
正常并行步数 = 全部计算块数 + 2 × tile数
本模型预取额度足够，不需要额外的未完成输入补齐步。
```

| op | tile数 | 计算块 | 完整并行步 | 本次有效步数 | 完整性 |
|---:|---:|---:|---:|---:|---|
| 0 | 48 | 3072 | 3168 | 2045 | 4096点仅前缀 |
| 1 | 24 | 1536 | 1584 | 1584 | 完整 |
| 3 | 12 | 768 | 792 | 792 | 完整 |
| 6 | 12 | 1536 | 1560 | 1560 | 完整 |
| 67 | 6 | 768 | 780 | 780 | 完整 |

每个完整算子都有一次phase5→19初始加载，随后各并行步18→19。
因此phase19数量比phase18多1；该关系及完整步数均已离线核对。
op0前缀仅覆盖5.64164 ms，不能拿它当整个op0。
完整op0改从头事件窗口取得：三次为8.70025～8.70656 ms。

#### 11.4 从波形与源码看，收益来自哪里

R6.2是块内MAC后再量化，行聚合后写DDR；下一tile仍要等待输入准备。
R6.3使用同一套MAC，上一块量化、旧行输出和下一tile预取与当前MAC重叠。
本版没有增加MAC吞吐、没有改变MAC总量，也没有再次扩大R6.2已有的行输出burst。
横向halo仅减少9197个有效输入word，约0.523%，不能解释39.785 ms整网收益。
代码差异、先前RTL任务重叠证据，以及当前板级并行步周期共同支持调度收益的解释。
本次没有分别关闭三项优化做消融实验，不能将整网收益精确拆成三项独立百分比。

板上只有event/valid/counter三个探针，没有内部任务busy或AXI握手探针。
以下“有写回/有预取”来自源码步骤与实际事件序号对应；
周期来自ILA实测，但不能单靠这些探针分离MAC、量化、DDR各自的忙或停顿时间。
并行步内各任务时间不能相加，也不能把整步都记作DDR耗时。

**op3：短1×1计算容易被行写回与预取所在步骤拖长。**

```text
纯MAC块预算 = (IC/4) × K × K × NX = 4×1×1×16 = 64周期
无行写回、无预取的常规计算+量化步 = 111周期
无行写回、有预取的计算+量化步 = 132～167周期
有行写回、无预取的计算+量化步 = 424周期
有行写回、有预取的计算+量化步 = 540～575周期
```

完整op3为190560周期：初始加载7689周期，并行步合计180208周期，
步间控制2413周期，描述符/权重/量化参数阶段合计250周期。
带行写回标志的步骤合计101188周期，占整op的53.10%。
这53.10%包含同时进行的计算、量化和预取，不能等同于纯写DDR占比。
它表明进一步只加快1×1乘法，可能仍被共享访存任务和逐步屏障限制。

**op6：计算更长，普通预取可隐藏，写回步骤仍长。**

纯MAC块预算128周期；无写回时，不预取和预取的常规步骤都约175周期。
有写回而不预取时约828周期，有写回并预取时946～983周期。
完整op6为437878周期，其中并行步417215、首tile加载15457、
步间控制4717、描述符/参数等489周期。
它支持“普通输入预取已重叠，但行输出与预取串在一个memory任务内仍会拖慢部分步骤”。

**op67：长3×3计算已接近纯MAC预算。**

```text
单块纯MAC预算 = (64/4) ×3×3×16 = 2304周期
768个含计算步骤全部实测2351周期，即每步比预算多47周期
纯MAC预算 = 768×2304 = 1769472周期 = 17.69472 ms
```

| op67组成 | 周期 | 时间ms |
|---|---:|---:|
| 描述符、权重、量化参数阶段 | 9545 | 0.09545 |
| 首tile输入加载 | 26097 | 0.26097 |
| 768个含计算并行步 | 1805568 | 18.05568 |
| 6个末块量化步 | 462 | 0.00462 |
| 6个末行写回排空步 | 6774 | 0.06774 |
| 步间控制 | 2359 | 0.02359 |
| 合计 | 1850805 | 18.50805 |

有无预取、是否包含旧行写回，op67的含计算步骤均为2351周期。
结合源码和RTL验证，说明这些步骤内访存被较长计算覆盖。
47周期差额包括调度、流水线及任务交接等，不能全部归为MAC核内部开销。
整op比纯MAC预算仅多0.81333 ms，继续用同一阵列做通用调度的空间已较小。

全网补齐通道MAC仍为670728192，纯MAC预算104.80128 ms，
有效吞吐约4.228 GMAC/s，预算时间/实测时间为66.06%。
这不是ILA测得的DSP有效忙占比，剩余53.83972 ms也不能全部视为DDR停顿。

不能直接与125.5个BRAM Tile相减；实际映射还涉及端口、打包及其他模块。
Vivado会继续优化、常量传播、删除或共享逻辑，同时整机还包含摄像头、HDMI、互连及ILA。
因此估算不是整机资源的简单上下界，也不能把整机新增33个BRAM Tile全部归给某个缓存。

当前仅余14.5个BRAM Tile和43个DSP；
Slice已用94.80%，即使LUT只用59.58%，可放置空间也没有表面上那么宽裕。
LUT/FF的配对、控制集及布线会影响Slice打包，后续优先复用缓冲和计算资源。

100 MHz的`clk_fpga_0`时钟域：WNS=+0.107 ns、WHS=+0.036 ns，域内TNS=0。
但整机WNS=-0.533 ns、TNS=-2.586 ns、7个setup端点失败，**整机时序尚未全部通过**。
主要失败集中在HDMI 500 MHz时钟I，最差路径涉及绿色通道的
`data_rise_s_reg[0]→ODDR2_inst0/D1`，半周期要求1 ns。
该HDMI域TNS=-2.568 ns，不把整机全部负裕量都归给HLS。
本次未修改HDMI或约束；不能因板上可运行或HLS域通过就宣称整机时序收敛。

### 12. 板测后的下一步优化方向

**通用调度已有明显收益，下一步优先做1×1算子专项HLS优化。**
这仍需修改HLS中的算子计算、数据组织或调度；不意味着HLS已经没有优化空间。
目前没有证据要求先改网络结构、减少通道或重新训练。

3×3仍占105.928 ms，是绝对耗时大头；
但其纯MAC预算88.68096 ms，差额17.24704 ms，op67等大层已接近阵列预算。
43条1×1占41.141 ms，纯MAC预算16.12032 ms，差额25.02068 ms。
差额包含可隐藏和不可消除的控制、量化、搬运等，并非都能回收；
它说明在不增加阵列的前提下，1×1专项是更值得优先验证的方向。

| 优先级 | 方案 | 用本次证据验证什么 |
|---:|---|---|
| 1 | 1×1专用短路径，简化k循环及地址/控制 | op3/6/45/48/68周期及数值 |
| 2 | 连续处理更多1×1块，减少任务启动与排空 | 短块111/175周期能否降低 |
| 3 | 调整1×1访存粒度与写回/预取安排 | 带写回步骤能否缩短，避免转成DDR瓶颈 |
| 4 | 再评估op0的IC补齐及输入组织 | 8.690 ms相对4.42368 ms差额 |
| 5 | 后续再评估Copy融合、跨算子复用或模型侧优化 | 兼容性、片上容量和精度代价 |

前三项需要联动设计：仅加速1×1乘法，不解决memory串行与步骤屏障，整层收益可能很小。
优先共用现有MAC及缓冲，不能直接另复制整套1×1阵列或大IFM bank。
若改NX、块批量或缓存布局，必须重新检查实际BRAM、Slice、时序及AXI事务。

以下仅是假设“1×1整类耗时下降，其余部分不变”的目标换算，不是综合或板测预测：

| 1×1整类耗时下降 | 整网时间 | 对应FPS |
|---:|---:|---:|
| 20% | 150.413 ms | 6.65 |
| 30% | 146.299 ms | 6.84 |
| 50% | 138.071 ms | 7.24 |

若1×1不现实地完全降到纯MAC预算，整网仍为133.62032 ms，约7.48 FPS；
这是固定其他耗时的乐观算术界限，不是可达到的承诺。
下一版先用独立标量及整网arena验证数值，再做同输入RTL、资源/时序与板测对照。
本次记录不实施这些后续优化，R6.3 / 9.xsa保持已验证实现。

### 13. 修改前后代码示例与用法

本版新增第11节板测和第12节后续方案，代码对照顺延到第13节。
R6.1/R6.2末尾的历史对照保留，本节补充R6.2到R6.3的变化。

#### 13.1 计算、量化和输出重叠

```cpp
// 修改前：R6.2按块串行，行就绪再写DDR。
// MAC(block_i);
// requant_to_row(block_i);
// if (row_ready) write_row_to_ddr();

// 修改后：节选r63_wave，以下变量均为它的真实参数。
#pragma HLS DATAFLOW
r63_memory(p_act, next_ifm, halo, res_write, row_read,
           c, current, next, compute, store,
           quota, reuse, load_g, load_r);
r63_mac(current_ifm, weights, bias, acc_write,
        c, current, compute);
r63_quant(acc_read, res_read, mq, shift, row_write, c, quant);
// 三个任务都返回后，才交换缓冲所有权。
```

示例省略函数声明及STABLE指令；完整可综合代码见实现头文件。
不能仅给旧Conv加DATAFLOW，也不能让MAC和量化读写同一acc bank。
本版通过valid控制首步填充和末尾两步排空，不复制MAC阵列。

#### 13.2 下一tile预取

```cpp
// 修改前：当前tile结束后，才完整加载下一tile。
// load(tile_i); compute(tile_i); load(tile_i_plus_1);

// 修改后：memory在各并行步内预取若干输入行。
int quota = 1;
if (next_rows > blocks)     quota = 2;
if (next_rows > blocks * 2) quota = 4;
if (next_rows > blocks * 4) quota = 8;
if (next_rows > blocks * 8) quota = 16;
// 当前IFM只读；下一IFM只由memory写入。
// 完整准备并排空当前输出后，input_bank才翻转。
```

Vitis仍传16，内部宽度选择保留R6.2用法；
预取额度是硬件内部调度参数，不需要软件新增寄存器配置。

#### 13.3 相邻横向tile重叠列复用

```cpp
// 修改前：新tile的整个有效窗口都从DDR重读。
// next_ifm[base + x] = src[read_base + x];

// 修改后：先取保留列，再从DDR读取其余有效区间。
for (int x = 0; x < kept; ++x)
    next_ifm[base + x] = halo[cache_base + x];
// 这里省略边界补零分支。
for (int x = start; x < end; ++x)
    next_ifm[base + x] = src[read_base + x];
// 本行完全准备后，保存右边重叠列供下一个横向tile使用。
for (int x = 0; x < overlap; ++x)
    halo[cache_base + x] = next_ifm[base + cols - overlap + x];
```

`kept`仅在同一tile行、相邻窗口且缓存容量足够时非0。
换行、没有重叠或容量不足时为0，自动沿用DDR读取路径。
数据总布局、输入值及量化顺序保持不变。

### 1. 前提、范围与冻结基线

其中43条1×1合计41.141 ms，纯MAC预算16.12032 ms；
op3/6的ILA显示短计算块与逐步屏障、写回/预取组合仍有明显开销。
本版针对该调度问题，不改变模型、权重、描述符、MAC数量或量化数值顺序。

部署版本为 **10.xsa**，完整命名建议为`yolov5n_speed_wrapper_10.xsa`。
它由用户在Vivado更新IP并完成硬件流程后导出，HLS不直接生成XSA。

用户完成10.xsa部署后的板测证据另见第10节，不与小规模RTL用例混用。

32位gmem、AXI-Lite寄存器、event/valid端口及C4布局保持原接口。

摄像头、HDMI、AMP双核代码均不修改。

### 2. 快路径选择及兼容范围

HLS解释当前描述符后，仅在以下条件同时成立时选择1×1行级路径：

```cpp
kk == 1 && ss == 1 && pad == 0 && add_off < 0
&& ih == oh && iw == ow
```

真实84条描述符中的43条1×1全部满足。
3×3、1×1带残差、stride=2或非零padding等情况继续按块调度。
这是运行时选择，Vitis不增加模式参数，也不修改tile_c=16的原表。
实际内部tile宽度仍按IFM容量选择64/32/16。

快路径保留`y→x块→ob→ib→nx`对应的计算顺序，
每个输出的输入通道组累加顺序和dot4表达式不变。
两种卷积共用一个`r64_mac`任务和同一处乘法表达式；
不模板化生成第二套1×1阵列，不把更多DSP当作本版收益来源。
共享任务的控制有所变化，兼容路径的周期也必须实测，不能宣称逐周期不变。

### 3. 从逐块屏障改成行内MAC/量化流

R6.3每个计算块都进入一次wave，并交接上一块acc及更早的输出。
R6.4快路径一次wave处理一个输出行，MAC连续遍历该行的x块和ob。
累加器仍为16×16；每个像素完成最后一组输入通道累加后，
将16个int32结果打包成512位数据，经深度16的FIFO交给量化任务。
量化任务消费当前行结果，保留原mq/shift、Leaky、sat8及打包顺序。

```text
输出行y的wave：
MAC    ：连续计算行y的各x/ob块，完成像素→FIFO
quant  ：FIFO→原定点量化→当前行缓存
memory ：写回已完成行y-1，同时准备下一tile输入
         ↓ 三个任务都结束，交换行缓存所有权
tile结束：再用一个wave排空末行写回
```

FIFO逻辑容量为16×512 bit=1024 B，使用LUTRAM，未新增大IFM或整行acc数组。
FIFO满会阻塞MAC，空会阻塞量化；不能用C仿真的无界队列代替RTL反压验证。
每个有效像素、每个有真实输出通道的ob恰好生产/消费一个包。
尾像素不发包；若自定义描述符多补齐整个空ob，也不为其发包，防止消费数量不匹配。
每次wave结束FIFO必须为空，C仿真带断言，RTL另检查握手、容量和退出余额。

旧块级路径仍使用两套acc/res bank，快路径量化使用FIFO。
当前行量化与上一行写回使用不同的row bank；tile切换前排空输出。
下一tile输入完整准备后才切换IFM bank。
不扩展为任意源/目标重叠别名支持，维持当前模型分离源/目标的使用前提。

按真实描述符计算，43条1×1的wave总数从9384降为2064，减少78.01%。
op3从792降为204，op6从1560降为204。
这是任务启动和屏障数量，**不是整层耗时减少78%**。
MAC、量化、有效输出字数及输入DDR字数并未按这个比例减少。
模型预算和覆盖检查见`r6_4_geometry.json`。

### 4. 保留burst的AXI读写配对

快路径每个输出行分配`icb=IC/4`个下一tile输入C4行。
后继tile高度不大于当前tile，因此该额度足够，不需要运行时整数除法。
不沿用旧块级配额的16行上限，也不向2的幂过度取整。
真实模型不存在因此产生的额外输入补齐行。

当旧输出行与下一输入行同宽、仍有输入额度且绝对DDR范围不重叠时，
`r64_pair_rows`启动一个连续读进程和一个连续写进程，
分别使用AXI的读、写方向；两侧仍按行推断burst。
父memory任务等待两侧完成后才推进输入游标，再执行剩余工作。
整个wave仍由memory层统一安排DDR，MAC与quant不直接访问DDR。

这是读/写两个方向的配对，不是让多个输入读进程竞争同一读口。
DDR控制器仍需仲裁真实存储器带宽，并不保证板上每拍同时完成一个读字和一个写字。
尾tile宽度不同、输入已准备完、没有后继tile或范围检查不通过时，
保留独立的行写回/输入读取路径。
1×1无halo，3×3横向重叠列复用继续沿用R6.3。

#### 10.4 源码与ILA如何共同解释本次收益

**变化是1×1的交接粒度和读写安排，不是增加MAC阵列。**
R6.3每个x/ob计算块都启动wave，量化上一块、写更早的行，wave结束后再推进。
R6.4在一个wave内连续计算同一行的全部x/ob块，完成像素后通过512位FIFO交给量化。
memory写上一行，并在满足同宽、额度及无重叠前提时配对读下一tile输入。
同一套64 MAC/周期计算阵列、MAC数量及数值顺序保留，输入有效字数也没有因此减少。

| 对照 | R6.3 | R6.4 |
|---|---|---|
| op3每tile | 64个计算块+2次排空 | 16个行计算+1次排空 |
| op3完整wave | 792 | 204 |
| op6完整wave | 1560 | 204 |
| op45完整wave | 204 | 102 |
| op68完整wave | 780 | 102 |
| 43条1×1合计wave | 9384 | 2064，减少78.01% |

wave数减少78.01%，但1×1时间只下降21.52%，因为每个新wave包含更多计算块。
不能直接把R6.3一个块的111/175周期，与R6.4一整行的462/1370周期比较后认定变慢。
须比较相同输出范围或整层时间，原有MAC和有效数据搬运仍需完成。

本次板上只测event/valid/counter；下面的任务组合来自源码调度与事件序号映射。
周期来自ILA，任务标签属于源码推断，不是探针直接测得的busy状态。
没有板级AXI握手或FIFO占用探针，不能宣称已经测得板上同时读写的拍数。
第6节的同拍768次读写、FIFO反压及burst证据来自同输入RTL仿真。
没有分别关闭行级流和读写配对做消融实验，不能拆出两者各自独立贡献的毫秒数。

**op3：逐块屏障大幅减少，短行仍受搬运及流水线交接影响。**

op3的内部tile宽64、IC16/OC16，每行包含4个NX16计算块。

**op6/op68：长行计算已能覆盖当前写回和预取组合。**

op6每行8个计算块，纯MAC为`8×(32/4)×16=1024`周期。
192个含计算行wave，无论是否写旧行、是否预取，都恰为1370周期。
12个末行排空wave为858～860周期。
整层可复算为`493+15371+273338+649=289851`周期，即2.89851 ms。
对比R6.3的4.37878 ms，减少约33.80%，与串口33.79%吻合。

op68每行同样8块，纯MAC为`8×(64/4)×16=2048`周期。
96个含计算行wave均为2394周期，有无旧行写回/下一tile预取不改变其长度。
6个末行排空wave为1186～1190周期，整层2.60826 ms。
这两层说明当前组合下再缩短普通搬运未必能缩短含计算wave；
仍不能从包络唯一断言每拍DSP忙，计算任务内部固定成本和首尾开销仍有优化空间。

**op45：输入准备仍是值得继续测量的方向。**

op45是IC64/OC16，内部tile宽32，每行只有2个计算块，纯MAC为512周期。
末tile无预取的16个含计算行wave均648周期；
有旧行写回且预取的75个wave为1374～1404周期，均值1383.52周期。
加上下一tile准备后wave明显变长，说明这一任务组合仍限制短计算行。
同类op48也仅降低约14.86%，收益弱于op3/6，与该现象一致。
进一步定位需补AXI AR/R、AW/W/B握手或memory任务busy，区分带宽、等待和控制成本。

**op67：兼容3×3保持原预算附近，继续通用调度的余量较小。**

768个含计算块wave仍全部2351周期，与R6.3相同；单块纯MAC预算2304周期。
本次合计`9545+25694+1813026+2369=1850634`周期，即18.50634 ms。
对比R6.3 ILA的18.50805 ms基本不变，整层比17.69472 ms纯MAC预算多约0.812 ms。
仅消除外层启动屏障，无法让这类大3×3层得到类似op3的相对收益。

**极短Detect real3输出不保证受益。**

op77为0.22873 ms，首tile准备11130周期，已占完整22873周期的约48.66%。
无预取的含计算行wave为344周期，有预取/写回时约699～726周期；
仅3个真实输出通道减少了有效输出字数，并没有减少补齐后的16路MAC工作。
op83仅一个tile，首tile准备6789周期，占9377周期的约72.40%。
因此短头输出应看初始化、通道利用率及输入准备，不能期待减少wave就必然加速。
本次不据单次微秒差直接调整快路径阈值，需同输入RTL和重复板测共同验证。

全网补齐MAC仍为670728192，纯MAC预算104.80128 ms。
本次有效吞吐约4.477 GMAC/s，预算时间/实测时间为69.95%。
这是算术预算比，不是ILA直接测得的DSP有效忙占比；
与纯MAC预算相差45.02172 ms，也不能全部解释为DDR停顿或可消除成本。

#### 10.5 Vivado实际资源、时序及实现边界

[布局后资源报告][r64-board-util]时间16:55:14，
[布线后时序报告][r64-board-timing]时间16:57:56，均早于本次XSA导出。

| 整机项目 | R6.3实际 | R6.4实际 / 容量 | 本次占比 |
|---|---:|---:|---:|
| LUT | 31697 | 36052 / 53200 | 67.77% |
| FF | 41916 | 46608 / 106400 | 43.80% |
| BRAM Tile | 125.5 | 125.5 / 140 | 89.64% |
| DSP | 177 | 187 / 220 | 85.00% |
| Slice | 12609 | 12692 / 13300 | 95.43% |

相比R6.3，LUT增加4355、FF增加4692、DSP增加10、Slice增加83，BRAM Tile不变。
这些是整机实现差异，不能将每个新增资源都唯一分配给FIFO或某一个函数。
HLS仍只有一套64 MAC/周期阵列，整机DSP187也不能直接当成187个并行MAC。

HLS估算51062 LUT、47994 FF、128 DSP、152 BRAM_18K，与上表不是同一统计口径。
HLS统计独立模块并估计映射，Vivado进一步常量传播、删除/共享逻辑和技术映射；
整机还含摄像头、HDMI、互连、计数器和ILA，实际打包及布局也影响结果。
BRAM_18K与BRAM Tile单位不同，152个18 Kb容量单位不能直接与125.5个Tile相减。
因此HLS估算不是Vivado整机实际资源，也不是可直接相加的确定上界或下界。

当前余量仅14.5个BRAM Tile、33个DSP和608个Slice。
LUT尚余约32%，不代表还能轻松复制一套计算阵列或大缓冲；
Slice打包、控制集和布线空间比LUT百分比更紧，后续优先复用现有资源。

100 MHz的`clk_fpga_0`域WNS=+0.319 ns、TNS=0、WHS=+0.036 ns，域内setup/hold通过。
但整机WNS=-0.762 ns、TNS=-2.732 ns，共5个setup端点失败，**整机时序仍未全部收敛**。
其中HDMI 500 MHz时钟I域4个端点失败，TNS=-2.685 ns；
另一个是像素时钟`axi_dynclk_0_PXL_CLK_O→I`路径，WNS/TNS=-0.047 ns。
不能把这些全部归给HLS，亦不能因HLS域通过或板上可运行就忽略整机报告。
本次没有修改HDMI或约束；后续硬件优化应同时检查这些路径的实现和约束。

### 11. 板测后的下一步优化方向

**建议从通用调度转向算子专项与数据流优化，但仍然需要做HLS。**
R6.4本身已经是1×1算子专项调度；“继续HLS”和“优化算子”并不是互斥选项。
下一步先保持模型数值和权重，针对具体层改计算组织、地址/搬运及算子间数据流。
改变网络算子、删通道或换轻量结构属于另一层面的模型优化，收益更大时再结合精度评估。

| 当前类别 | 实测ms | 纯MAC预算ms | 差额ms |
|---|---:|---:|---:|
| 3×3 | 105.984 | 88.68096 | 17.30304 |
| 1×1 | 32.289 | 16.12032 | 16.16868 |
| Copy | 10.651 | 不适用 | 不适用 |

3×3已占70.74%，是下一阶段绝对计算量的重点；
但op67等大层已接近现有阵列预算，不宜再期待通用屏障优化带来大比例收益。
1×1仍有相近的预算差额，并不意味着16.169 ms可以全部回收。
应按下面的波形证据选择专项，先做小范围验证再决定完整版本。

| 优先级 | 方向 | 现有证据与下一步验证 |
|---:|---|---|
| 1 | op0及短计算层的输入组织/访存专项 | op0为8.735 ms，预算4.424 ms；补AXI与memory探针 |
| 2 | 1×1按IC/OC形状优化控制和输入复用 | op45预取行约1384周期、无预取648；op6/68长行计算占主导 |
| 3 | Copy/拼接/上采样的数据流融合 | 当前10.651 ms；核对生产者直接写目标和多消费者生命周期 |
| 4 | 3×3计算映射及通道利用率 | 大层已近预算，评估阵列内重排而非直接复制更多DSP |
| 5 | 需要更大提升时做模型算子/通道优化 | 需重新导出描述符/权重，并验证检测精度与量化误差 |

op0有效RGB的MAC预算为3.318 ms，但当前按IC4执行，硬件预算是4.424 ms。
仅把第4通道零乘法跳过不会自动减少固定CO16×CI4阵列的周期；
必须改变工作映射、打包或计算组织，才可能将空闲乘法资源转成有效吞吐。
同时op0相对硬件预算仍有4.311 ms差额，先测加载/写回和短块控制比盲目删零乘法更有依据。

op45/48可优先验证下一tile输入的连续访问、输入复用和搬运粒度。
op6/68则应检查行内块边界、参数/地址选择和固定交接，
因为它们的含计算wave在有无预取时长度相同，单纯加快同一段搬运未必有效。
所有方案都需保留burst，检查AXI有效字数/地址、FIFO反压、全arena数值及实际资源。

Copy优化可能需要算子生成脚本、描述符、arena分配及Vitis协同，不能承诺仅改HLS就能零拷贝。
需保持C4对齐、源目标别名关系、多消费者和缓存维护正确；上采样融合还需保留坐标语义。
real3的op71/77/83合计仅0.901 ms，修复局部回退有意义，但不应作为全网大幅提速主线。

若目标是明显超过现有MAC预算，才进一步评估剪枝、通道缩减或更轻的3×3替代结构。
这些会改变网络计算量，通常需要训练/微调与精度验证；不能把普通卷积直接替换成深度卷积。
当前DSP和Slice余量较小，扩大阵列前必须先评估整机实现能力。

以下仅为“其他耗时不变”的条件换算，用于决定投入优先级，不是下一版实测预测：

| 假设条件 | 整网时间 | 对应FPS |
|---|---:|---:|
| 当前1×1整类再减少20% | 143.365 ms | 6.98 |
| 当前1×1整类再减少30% | 140.136 ms | 7.14 |
| 当前Copy时间减少50% | 144.498 ms | 6.92 |
| 当前3×3整类减少10% | 139.225 ms | 7.18 |

达到7 FPS需整网降至142.857 ms，即再节省约6.966 ms；达到8 FPS则需再节省24.823 ms。
不能把各方案的假设收益简单相加，因为它们可能优化同一段等待，或产生新的资源/带宽成本。
本次只记录路径，不实施下一版HLS、模型或Vitis修改，10.xsa保持已验证实现。

### 12. 修改前后代码示例与用法

本版新增板测和后续方向后，代码对照顺延至R6.4末尾第12节。
R6.1/R6.2/R6.3各自末尾的历史代码对照保留。

#### 12.1 行级流调度替代逐块交接

```cpp
// 修改前：R6.3每块都返回wave，并在外层交接acc和下一块元数据。
// r63_mac(..., compute);
// r63_quant(..., previous);
// wave结束后才能进入下一块。

// 修改后：节选R6.4 wave的真实调用，快路径一次处理当前行。
hls::stream<r64_acc_packet> packets("pointwise_acc");
#pragma HLS STREAM variable=packets depth=16
#pragma HLS BIND_STORAGE variable=packets type=fifo impl=lutram
r64_mac(current_ifm, weights, bias, acc_write,
        c, current, compute, packets);
r64_quant(acc_read, res_read, mq, shift, row_write,
          c, current, quant, packets);
```

完整`r64_wave`还包含DATAFLOW、只读STABLE和memory调用，不能仅复制这段当成串行替换。
快路径`quant=compute`表示消费当前行FIFO；兼容路径仍使用上一块元数据。
Vitis无需显式选择，描述符满足第2节条件即可。

#### 12.2 输入额度与burst读写配对

```cpp
// 修改前：按计算块数给1/2/4/8/16个输入行额度；写回与预取串行。
// write_old_row(); prefetch_next_rows(quota);

// 修改后：1×1每输出行准备IC/4个输入C4行。
if (pointwise) quota = c.icb;

// 同宽、存在后继输入、额度有效且DDR范围不重叠时：
r64_pair_rows(p_act, next_ifm, output,
              c.src_off, read_base, ibase,
              c.dst_off, base, q, current.nc);
// r64_pair_rows内部DATAFLOW：一个连续读进程 + 一个连续写进程。
// 其余形状保留原独立读/写路径，不能取消边界和范围检查。
```

#### 12.3 固定切片控制流数据选择资源

```cpp
// 早期候选：co是运行时通道，直接动态截取512位包，估算逻辑过大。
// source = packet.range(co * 32 + 31, co * 32);

// 最终实现：展开固定切片，通道选择使用普通32位数组。
int32_t lanes[HW_CO];
#pragma HLS ARRAY_PARTITION variable=lanes complete
for (int lane = 0; lane < HW_CO; ++lane) {
#pragma HLS UNROLL
    lanes[lane] = (int32_t)(uint32_t)
        packet.range(lane * 32 + 31, lane * 32);
}
const int32_t source = pointwise ? lanes[co] : acc[nx][co];
```

这只改变数据选择实现，不改变int32累加结果、26位量化输入截取或最终输出字节。
主实现、测试及综合脚本均标注R6.4，部署编号为10.xsa。
